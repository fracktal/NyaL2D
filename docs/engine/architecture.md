# 자체 엔진 구조 제안

## 목표 (프로젝트 요구에서)

1. 상용 수준 품질: 매끄러운 변형, 깨끗한 가장자리, 주사율과 무관한 물리, 안정된 파일 형식.
2. 계속 발전·수정 가능: 우리가 전부 소유하고, 기능을 단계적으로 더할 수 있는 구조.
3. AI-native: LLM이 모델을 읽고, 고치고, 결과를 눈으로 확인할 수 있어야 한다.
4. Live2D 호환은 필요 없음.

## 1. 큰 그림: 세 층

```
┌──────────────────────────────────────────────┐
│ 애니메이션 층 (TypeScript)                      │  모션·표정·포즈·시선·립싱크·자동 깜빡임
│  → 파라미터 값만 쓴다                            │
├──────────────────────────────────────────────┤
│ 코어 (Rust → WebAssembly / 네이티브 라이브러리)    │  형식 읽기·검증, 키폼 보간, 디포머,
│  입력: 모델 + 파라미터 + 경과 시간                  │  물리, 그리기 목록 만들기
│  출력: 꼭짓점 버퍼 + 그리기 목록                    │  (GPU 없이 동작, 결정적)
├──────────────────────────────────────────────┤
│ 렌더러 (플랫폼별, 얇게)                           │  웹: WebGL2 기본 + WebGPU
│  그리기 목록 → 화면                              │  헤드리스: 테스트·AI 검증용 이미지 출력
└──────────────────────────────────────────────┘
```

- 코어는 그래픽 카드를 모른다. 그래서 브라우저, 데스크톱 앱, 서버(AI가 결과를 이미지로 확인하는 곳), 나중에 Unity 같은 게임 엔진에서도 같은 코어를 쓴다.
- 렌더러는 "삼각형 그리기, 마스크, 블렌드"만 한다. 플랫폼마다 수백~천여 줄 수준으로 작게 유지한다.

## 2. 언어 선택

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| **A. 코어 Rust + 웹 렌더러 TypeScript (추천)** | 빠르고 메모리 안전. 한 코드로 웹(WASM)·데스크톱·서버·게임 엔진 모두. 결정적 계산과 테스트가 쉬움. 상용 SDK로 팔거나 배포하기 좋음 | 빌드 도구가 하나 더 늘어남(Rust 툴체인). 디버깅이 TS보다 약간 번거로움 |
| B. 전부 TypeScript | 지금 앱과 같은 언어. 시작이 가장 빠름 | 브라우저 밖(네이티브, 게임 엔진)으로 가기 어렵다. 큰 모델에서 성능 한계 |
| C. 전부 Rust + wgpu | 렌더러까지 하나로 | 웹 번들이 커지고, 브라우저 쪽 디버깅·통합이 어렵다 |

추천은 **A**. 이유: "계속 발전하는 런타임"이 목표라면 결국 웹 밖에서도 돌아야 하고, 코어를 한 번만 만들면 된다. Live2D도 공개 문서상 같은 구조(C 코어 + 플랫폼별 프레임워크)를 쓴다.
코어 API는 아주 작게(모델 로드, 파라미터 쓰기, 갱신, 결과 읽기) 유지해서 TypeScript 쪽에서 얇은 래퍼로 감싼다.

## 3. 모델 파일 형식 (초안 방향)

- 이름(가칭): `.nyal` 패키지 = 폴더 또는 zip
  - `model.json`: 사람과 AI가 읽고 고칠 수 있는 원본. 버전 번호 필수.
  - `textures/*.png`: 텍스처.
  - (나중에) `model.bin`: 배포용 압축 바이너리. 원본에서 자동 생성.
- 원칙
  - 모든 오브젝트에 **안정된 ID**와 사람이 읽는 이름, 의미 태그(`eye.left`, `hair.front`)를 둔다. AI가 "왼쪽 눈"을 찾을 수 있게.
  - **JSON Schema로 형식을 정의**하고, 검증 오류는 "어디가 왜 틀렸는지"를 문장으로 알려준다. AI가 스스로 고치게.
  - 버전마다 **마이그레이션**(옛 파일 자동 변환)을 제공한다. 1.0 이후에는 깨지는 변경 금지.
  - git으로 비교하기 쉽게 정렬된 키, 숫자는 고정 소수점 자리수.
- 주요 블록
  - `parameters[]`: id, 범위, 기본값, 반복 여부(360도 회전용), 그룹.
  - `nodes[]`: 트리. 종류 `part` / `warp` / `rotate` / `bone` / `mesh`. 노드마다 의미 태그, 레이어 깊이(선택), 메시는 꼭짓점별 깊이(선택).
  - 키폼마다 생성 출처(`generatedBy`, 손으로 고쳤는지). 자동 생성을 다시 돌려도 사람이 고친 부분은 보존. ([auto-angle-generation.md](auto-angle-generation.md))
  - 각 노드의 `keyforms`: 반응하는 파라미터 축 목록 + 키 값 + 축 조합별 값(꼭짓점, 각도, 불투명도, 색, 그리기 순서).
  - `shapes[]`: 가산 블렌드 셰이프.
  - `masks`: 메시별 마스크 목록, 반전 여부.
  - `physics[]`: 입력(파라미터, 가중치), 체인(질점, 길이, 무게, 저항), 출력(파라미터, 배율).
  - `glue[]`: 꼭짓점 쌍과 강도.
- 애니메이션 파일(모션·표정·포즈)은 별도 파일. 코어 형식과 버전을 따로 관리.

## 4. 코어 내부 설계

- **데이터 지향**: 로드할 때 트리를 평평한 배열로 바꾸고 부모가 자식보다 먼저 오게 정렬. 프레임마다 메모리 할당 없음.
- **변경 추적**: 파라미터가 바뀐 오브젝트만 다시 계산(대부분의 프레임에서 일부만 바뀜).
- **결정성**: 같은 입력 → 같은 출력. 물리는 고정 시간 간격. 테스트에서 오차 허용치를 정해 비교.
- **조회 API**: "변형 후 이 메시의 화면 경계", "이 점에 어떤 메시가 있나(클릭 판정)", "이 파라미터가 영향을 주는 노드 목록". Iki에 없어서 아쉬웠던 부분(`docs/iki/known-limitations.md`).
- **편집 친화**: 모델 일부만 바꿔도 전체를 다시 로드하지 않고 해당 노드만 갱신하는 API. 에디터와 AI 편집의 속도를 좌우한다.

## 5. 렌더러 설계 (웹)

- 공통: 사전 곱셈 알파, 텍스처 밉맵/필터 설정, 고해상도 화면(devicePixelRatio) 대응, 투명 배경 출력.
- 마스크: 마스크 텍스처 아틀라스 방식(채널별 4개씩 묶기), 중첩·반전 지원.
- 블렌드: 기본/더하기/곱하기는 즉시, 스크린·오버레이 등은 화면 밖 버퍼 경유.
- 배치: 같은 텍스처·같은 블렌드 연속 메시는 한 번에 그리기.
- WebGL2 경로부터 만들고, 같은 그리기 목록을 받는 WebGPU 경로를 나중에 추가.
- 헤드리스: Node에서 이미지 파일로 뽑는 경로(테스트의 기준 이미지 비교 + AI의 시각 검증).

## 6. 품질 보증

- **적합성 테스트 모델 세트**: 기능 하나당 작은 모델 하나(워프만, 회전 중첩, 마스크 반전…) + 기대 결과(꼭짓점 값, 기준 이미지).
- 코어 단위 테스트(Rust), 렌더러 이미지 비교 테스트(헤드리스 Chromium), 성능 기준(모델 크기별 프레임당 시간) 자동 측정.
- 퍼징: 깨진 파일을 넣어도 멈추지 않고 오류를 돌려주는지.

## 7. 저장소 구성 (제안)

```
engine/
  core/            Rust 크레이트 (형식, 평가, 물리)
  core-wasm/       WASM 바인딩
  web/             TypeScript: 로더, WebGL2/WebGPU 렌더러, 애니메이션 층
  spec/            형식 명세 + JSON Schema
  conformance/     테스트 모델과 기대 결과
  viewer/          최소 뷰어 (파일 끌어놓기, 파라미터 슬라이더)
app/               기존 편집 앱 (일시 정지, 나중에 엔진으로 교체)
```
