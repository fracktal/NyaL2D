# 2D 퍼펫 엔진은 어떻게 동작하나

Live2D류 "한 장 그림을 쪼개서 움직이는" 엔진의 공통 구조를 정리한다.
근거는 공개 문서(Live2D 에디터 매뉴얼의 용어·기능 설명), 일반 컴퓨터 그래픽스 기법, 이 저장소의 Iki 분석(`docs/iki/`)이다.
Ayagami와 Inochi2D는 AI가 코드를 분석하지 말라고 요청하므로 소스를 보지 않았다.

## 한 문장 요약

그림을 부위별 조각(메시)으로 나누고, "고개 각도" 같은 슬라이더(파라미터) 값에 따라 각 조각의 꼭짓점이 어디로 갈지를 몇 개의 예시 모양(키폼) 사이를 섞어서 정하고, 그 결과를 화면에 그리는 프로그램이다.

## 1. 모델을 이루는 것

| 구성 요소 | 뜻 | 비고 |
| --- | --- | --- |
| **텍스처** | 원화를 부위별로 잘라 한 장(또는 여러 장)에 모은 그림 | PSD 레이어에서 만든다 |
| **아트메시 (메시)** | 텍스처 한 조각 + 그 위에 깔린 삼각형 그물(꼭짓점, UV, 삼각형 목록) | 실제로 화면에 그려지는 유일한 것 |
| **파라미터** | 이름·최소·최대·기본값을 가진 슬라이더. 예: `angleX` -30~30 | 모델의 "조종 손잡이". 모션, 물리, 시선, 립싱크, AI가 모두 이 값을 쓴다 |
| **디포머** | 메시나 다른 디포머를 담아서 통째로 변형하는 틀 | 아래 2절 |
| **키폼** | 특정 파라미터 값에서의 모양(꼭짓점 위치, 각도, 불투명도 등) 스냅샷 | 아래 3절 |
| **파트** | 메시·디포머를 묶는 폴더. 불투명도와 표시 여부를 함께 제어 | 팔 A/B 전환 같은 데 쓴다 |
| **그리기 순서** | 어떤 메시가 앞에 오는지 | 파라미터에 따라 바뀔 수 있어야 한다(팔이 몸 앞뒤로 넘어갈 때) |
| **마스크(클리핑)** | 다른 메시 모양 안쪽에만 그리기 | 눈동자가 흰자 밖으로 안 나가게 |
| **물리 설정** | 파라미터 → 진자 → 파라미터 연결 | 아래 5절 |

## 2. 디포머: 변형을 층층이 쌓는 틀

- **워프(격자) 디포머**: 사각형 영역을 N×M 격자로 덮고, 격자 점을 움직이면 안의 내용이 고무판처럼 따라 휜다. 얼굴을 옆으로 돌리는 "입체감"의 핵심.
  - 격자 칸 안의 보간은 **쌍선형**(칸마다 직선)이 단순하고, **베지어/바이큐빅 패치**는 칸 경계에서도 매끄럽다. 상용 품질에는 매끄러운 쪽이 필요하다.
  - 안에 든 꼭짓점은 "격자 안의 상대 위치(0~1, 0~1)"로 저장해 두고, 매 프레임 격자 모양에 따라 화면 위치로 바꾼다.
- **회전 디포머**: 기준점, 각도, 크기, 이동을 가진 좌표계. 팔·목처럼 축을 중심으로 도는 부위. 워프로 크게 돌리면 모양이 쪼그라드는데, 회전 디포머는 그렇지 않다(Live2D 매뉴얼도 같은 이유를 든다).
- **중첩**: 디포머 안에 디포머를 자유롭게 넣을 수 있어야 한다. 예: 몸 기울기 워프 → 머리 회전 → 얼굴 각도 워프 → 눈 워프 → 눈 메시. 자식은 부모 좌표계 안에 있으므로 부모가 움직이면 따라간다.
- **(선택) 뼈대 스키닝**: Spine/DragonBones 방식. 꼭짓점마다 여러 뼈의 영향 가중치를 둔다. 머리카락·꼬리·천에 편하다. Live2D 계열은 주로 워프+회전으로 해결하지만, 우리 엔진은 둘 다 지원하면 표현 폭이 넓어진다.
- **글루**: 두 메시의 맞닿은 꼭짓점을 묶어 틈이 벌어지지 않게 한다(팔꿈치, 목 경계).
- **블렌드 셰이프(가산 변형)**: 기본 모양에 "차이값"을 더한다. 여러 파라미터 효과를 서로 간섭 없이 겹칠 때 좋다.

## 3. 파라미터와 키폼 섞기: 엔진의 심장

각 오브젝트(메시, 디포머)는 "어떤 파라미터들에 반응하는지"와 그 조합별 키폼을 갖는다.

- 예: 얼굴 워프가 `angleX`(-30, 0, 30) × `angleY`(-30, 0, 30)에 반응 → 3×3 = 9개 키폼.
- 현재 값이 `angleX=12, angleY=-5`라면, 각 축에서 양옆 키(0과 30, -30과 0)를 찾고 그 사이 비율로 **다중 선형 보간**한다. 파라미터가 N개면 2^N개 키폼을 섞는다.
- 축이 늘면 키폼 수가 곱으로 늘어나므로(3축×3키 = 27개), 상용 엔진들은 보통 한 오브젝트당 축 수를 2~3개로 제한하고, 그 이상은 **디포머를 중첩**하거나 **가산(블렌드 셰이프)** 으로 푼다.
- 꼭짓점뿐 아니라 불투명도, 그리기 순서, 곱하기/스크린 색, 회전 각도도 같은 방식으로 섞는다.
- 품질 포인트: 보간 결과가 키 사이에서 "꺾이지" 않게 하는 것. 단순 선형만 쓰면 고개를 돌릴 때 움직임이 딱딱해 보인다. 파라미터 값 자체에 이징을 걸거나, 키 사이를 스플라인으로 보간하는 선택지를 둔다.

## 4. 한 프레임의 계산 순서

1. **입력 모으기**: 모션 재생, 표정, 시선 추적, 립싱크, 사용자 슬라이더, AI 명령이 파라미터 값을 쓴다(우선순위·가중치 규칙 필요).
2. **물리 한 걸음**: 입력 파라미터를 읽어 진자를 움직이고, 출력 파라미터에 쓴다.
3. **키폼 평가**: 모든 오브젝트에 대해 3절의 보간을 수행. 값이 바뀌지 않은 오브젝트는 건너뛴다(캐시).
4. **디포머 적용**: 위에서 아래로(부모 먼저) 좌표를 변환해 모든 메시 꼭짓점의 최종 화면 위치를 얻는다.
5. **글루 등 후처리**.
6. **그리기 목록 만들기**: 그리기 순서 정렬, 불투명도 0인 것 제외, 마스크 관계 정리.
7. **렌더링**: GPU에 꼭짓점을 올리고 그린다.

1~6은 그래픽 카드 없이도 돌아가는 순수 계산이다. 이 부분을 **코어**로 분리하면 웹·데스크톱·서버(헤드리스 검증)에서 똑같이 재사용할 수 있다. Live2D도 공개 문서상 "Core(계산)"와 "Framework(플랫폼별 렌더링)"를 나눈다.

## 5. 물리

- 머리카락·리본·가슴 흔들림은 대부분 **진자(펜듈럼) 체인**으로 충분하다.
- 입력: 몸·머리 파라미터(위치 X, 각도 Z 등)를 가중치로 섞어 "몸이 얼마나 움직였나"를 만든다.
- 시뮬레이션: 질점 여러 개를 막대로 이은 체인. 매 걸음 중력·관성·공기저항을 적용하고 막대 길이를 지킨다. **Verlet 적분 + 거리 제약**(Position Based Dynamics 계열)이 안정적이고 구현이 짧다.
- 출력: 각 질점의 각도를 파라미터 범위로 정규화해서 `hairFrontSway` 같은 파라미터에 쓴다. 그러면 나머지는 3절의 키폼이 처리한다.
- 상용 품질 요건: **고정 시간 간격**(예: 1/120초)으로 돌려서 화면 주사율(60/144Hz)과 무관하게 같은 움직임이 나와야 한다. 탭이 백그라운드였다가 돌아올 때 폭주하지 않게 최대 걸음 수를 제한한다.

## 6. 마스크와 블렌드

- **마스크**: 두 가지 방법.
  - 스텐실 버퍼: 단순하고 빠르지만 부드러운 가장자리가 안 되고, 중첩 단계가 제한된다.
  - 마스크 텍스처: 마스크 모양을 화면 밖 텍스처에 먼저 그리고, 본 메시를 그릴 때 그 텍스처를 참조. 부드러운 가장자리, 여러 마스크 곱하기(중첩), 반전이 쉽다. 여러 마스크를 한 장의 큰 텍스처에 채널별로 모아(아틀라스) 비용을 줄인다. 상용 엔진은 대체로 이쪽.
- **블렌드 모드**: 기본(알파), 더하기, 곱하기는 GPU 블렌드 설정만으로 된다. 스크린·오버레이 같은 고급 모드는 아래 그림을 읽어야 해서 화면 밖 버퍼를 거친다.
- **곱하기/스크린 색**: 메시 색조를 파라미터로 바꾸기(볼 붉어짐, 그림자). 셰이더 몇 줄이다.
- **사전 곱셈 알파**(premultiplied alpha)를 처음부터 일관되게 써야 가장자리에 검은 테두리나 흰 테두리가 안 생긴다. 상용 품질에서 자주 나오는 결함이다.

## 7. 렌더링 기술 (웹 기준, 2026년 11월)

- **WebGL2**: 사실상 모든 브라우저에서 동작. 지금 Iki가 쓴다.
- **WebGPU**: Chrome/Edge(113+), Safari 26(macOS·iOS 26), Firefox(Windows 141+, Apple Silicon Mac 145+)에서 정식 지원. Linux·Android Firefox와 오래된 iPhone은 아직 빈틈이 있어 WebGL2 대체 경로가 필요하다. ([출처](https://www.utsubo.com/blog/frontier-web-apis-2026-production-ready))
- 결론: **WebGL2를 기본, WebGPU를 고성능 경로**로 둘 다 지원. 2D 퍼펫은 그리는 양 자체는 작아서 WebGL2로도 충분히 빠르고, WebGPU는 변형 계산을 GPU에서 하거나 여러 캐릭터를 동시에 띄울 때 이득이 크다.

## 8. 애니메이션 층 (엔진 바로 위)

- **모션**: 시간에 따른 파라미터 커브(선형·베지어·계단), 반복, 페이드 인/아웃, 우선순위.
- **표정**: 파라미터 값 묶음을 더하기/곱하기/덮어쓰기로 적용.
- **포즈**: 팔 A/B처럼 서로 배타적인 파트 그룹 전환.
- **자동 동작**: 눈 깜빡임, 숨쉬기, 시선 추적, 립싱크(음량 또는 음소).
- 이것들은 결국 "파라미터 값을 쓰는 것"이라 코어와 분리된 별도 모듈로 둔다.
